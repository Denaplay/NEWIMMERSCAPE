# Immerscape

## Публикация на новом хостинге

Сайту нужен хостинг с поддержкой Node.js 18 или новее. Статический файловый
хостинг без запуска `server.js` не подойдёт: сервер обслуживает API расписания
my-ERP и отправку уведомлений о новых бронях в Telegram.

В настройках хостинга укажите:

- команда запуска — `npm start`;
- команда сборки — не требуется;
- рабочая папка — корень репозитория;
- порт — переменная `PORT` обычно задаётся хостингом автоматически.

Добавьте в переменные окружения нового хостинга:

- `TELEGRAM_BOT_TOKEN` — токен внутреннего бота;
- `TELEGRAM_CHAT_ID` — ID чата Профсоюзной (сохранён для совместимости);
- `TELEGRAM_CHAT_ID_IZMAYLOVSKAYA` — ID чата Измайловской;
- `TELEGRAM_CHAT_ID_TAGANSKAYA` — ID чата Таганской.

Для супергруппы ID обычно начинается с `-100`. Вместо `TELEGRAM_CHAT_ID` можно указать
`TELEGRAM_CHAT_ID_PROFSOYUZNAYA`, если нужно единообразное имя.

Бот должен быть добавлен в каждый целевой чат и иметь право отправлять сообщения.
После изменения переменных перезапустите приложение. Адреса
`/api/my-erp/timetable/4893.json` и `/api/telegram-booking` обрабатывает обычный
Node-сервер, поэтому дополнительных правил перенаправления на стороне хостинга
не требуется. Ошибка Telegram не отменяет уже сохранённую бронь.

## Локальный запуск

Для интеграции с my-ERP сайт необходимо запускать через встроенный сервер-прокси:

```bash
npm start
```

После запуска откройте <http://localhost:3000>. Команда `npx serve .` раздаёт
только статические файлы и не проксирует my-ERP, поэтому браузер блокирует
внешний запрос по CORS.

Страница бронирования доступна по обоим адресам:

- <http://localhost:3000/booking>
- <http://localhost:3000/booking.html>

Чтобы выбрать другой порт:

```bash
PORT=8080 npm start
```

## Авторизация Supabase

Вход и регистрация работают через Supabase Auth по email и паролю. Публичные
параметры проекта находятся в `js/supabase-config.js`. В панели Supabase нужно:

1. включить провайдер **Authentication → Providers → Email**;
2. добавить адрес сайта (для разработки — `http://localhost:3000`) в
   **Authentication → URL Configuration → Redirect URLs**;
3. включить Row Level Security и настроить политики для всех таблиц с данными
   пользователей — publishable key сам по себе не даёт административных прав.

Чтобы имя и телефон сохранялись в отдельной таблице `public.profiles`, выполните
файл `supabase/schema.sql` в **Supabase → SQL Editor**. Скрипт создаёт защищённую
RLS-политиками таблицу, переносит данные уже зарегистрированных пользователей и
устанавливает триггер для новых регистраций. Без этого скрипта имя и телефон
находятся только в `auth.users.raw_user_meta_data`.

Страница `profile.html` показывает имя, телефон, email и `visits_count`. Имя и
фамилию пользователь может изменить самостоятельно. Количество фактических
посещений хранится в `public.profiles.visits_count` и должно увеличиваться вашей
CRM или администратором после состоявшегося квеста, а не при обычном бронировании.

### Разрешения сотрудников

Колонка `public.profiles.permission` принимает `operator`, `manager`,
`organizator` или `NULL` для обычного клиента. Назначать роли следует только из
SQL Editor/service-role окружения. `operator` видит сетку броней; `manager` также
редактирует/удаляет брони и видит клиентов; `organizator` дополнительно может
редактировать и удалять клиентов. После обновления `supabase/schema.sql` в
профиле сотрудника автоматически появляются ссылки на служебные страницы.

Клиент автоматически обновляет JWT через `refresh_token`. После развёртывания
этого обновления пользователям со старыми или отозванными сессиями может
потребоваться один раз выйти и войти снова, чтобы получить новую пару токенов.

Сетка объединяет записи сайта из `staff_bookings` с занятыми слотами расписания
my-ERP. Список клиентов строится из тех же броней и содержит контакты, квест,
дату, время и выбранные дополнительные услуги, поэтому данные не дублируются в
отдельную клиентскую таблицу.

В сетке показываются все слоты my-ERP. Цвета статусов: фиолетовый — служебный,
голубой — подтверждён, зелёный — был, жёлтый — недозвон, светло-зелёный —
ожидает предоплаты. Нажатие на время открывает компактную карточку брони;
нажатие на затемнённое пространство вокруг неё закрывает карточку.

Статус `closed`/«закрытый» выглядит как свободный тёмный слот, но время
перечёркнуто красной линией. Параметры `md5`, `code`, `hash` и `token`, которые
my-ERP возвращает в расписании, могут использоваться при разборе старых слотов,
но больше не отправляются при подтверждении новой брони с сайта.

Новые бронирования с формы сайта **не отправляются в my-ERP**. Расписание
`timetable/{id}.json` используется только для чтения доступных слотов.
Подтверждение формы вызывает Supabase-функцию `create_site_booking`, которая
одной транзакцией создаёт бронь со статусом `new` («Новое») в `staff_bookings`
и связанную запись клиента в `staff_clients`. Идемпотентный ключ защищает от
дублей при повторной отправке одного запроса; при ошибке транзакция целиком
откатывается и интерфейс показывает сообщение пользователю.

После обновления повторно выполните `supabase/schema.sql` в Supabase SQL Editor.
Список клиентов сотрудников загружается из `staff_clients`: менеджер может его
просматривать, а организатор — изменять и удалять записи.
Оператор может открыть любую бронь в сетке и изменить только её статус и поле
«Оплачено»; остальные поля для него доступны исключительно для чтения. В списке
клиентов комментарии отображаются обычным текстом, а дополнительные услуги —
коротким списком. Редактирование карточки клиента остаётся доступно организатору.
Дополнительные услуги хранятся отдельно от комментария заказа и показываются в
списке только названием и ценой, без описания услуги в скобках.
Поле комментария брони содержит только текст, введённый клиентом: автоматическая
строка вида `Описание: Магия и школа чародейства` больше не добавляется.
Если функция была установлена из предыдущей версии схемы и показывала ошибку
`column reference "booking_id" is ambiguous`, повторный запуск файла заменит её
исправленной версией без конфликта имени SQL-колонки и локальной переменной.

Слот без явного статуса брони и без клиентских данных больше не считается
подтверждённым: недоступный слот определяется как закрытый. Это предотвращает
ложную голубую подсветку прошедших или заблокированных дат.

Карточка принимает из ответа my-ERP статус, клиента, телефон, email, назначенного
сотрудника, оплату, предоплату и оба комментария, если эти поля присутствуют в
ответе API. Поскольку текущая интеграция my-ERP не предоставляет документированный
endpoint редактирования, изменения такой брони сохраняются как связанная запись
в `staff_bookings` с `source = 'my-erp'` и `erp_slot_id`; исходная запись my-ERP
при этом не изменяется.

### Если регистрация зависает или возвращает `{}`

Клиент прекращает ожидание через 20 секунд и показывает понятную ошибку. Причину
отправки письма нужно смотреть в **Authentication → Logs** панели Supabase.
Для SMTP Яндекса проверьте, что:

- `Username` — полный адрес реального почтового ящика без дополнительных слов;
- `Sender email address` совпадает с авторизованным ящиком;
- используется отдельный пароль приложения Яндекса, а не пароль от аккаунта;
- SMTP-доступ включён в настройках почтового ящика;
- после изменения SMTP выполнена тестовая регистрация на новый email.

Например, если ящик отправителя — `immerscape@yandex.com`, оба поля должны иметь
строго такое значение:

```text
Sender email address: immerscape@yandex.com
Username:             immerscape@yandex.com
```

Суффикс `'s Project`, название проекта и любые пробелы в `Username` недопустимы.
Для `smtp.yandex.ru` можно использовать порт `465`; пароль должен быть новым
паролем приложения для этого же почтового ящика. После сохранения настроек
следует повторить регистрацию с адресом, который ещё не зарегистрирован.

Пароли SMTP нельзя публиковать в репозитории, сообщениях или скриншотах. Если
пароль был раскрыт, его необходимо немедленно отозвать и создать новый.
